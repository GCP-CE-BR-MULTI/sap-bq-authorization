1 Visão Geral e Objetivos do Projeto

Documento de Arquitetura

Todos os dados transacionais e cadastrais do SAP (ECC ou S/4HANA) no ambiente Google Cloud e SAP estão sendo replicados de forma contínua via CDC (Change Data Capture) para o Google Cloud BigQuery. As visões analíticas de negócio são expostas aos usuários e dashboards por meio de camadas de views (camadas Raw, Conformed e Serving).

O Desafio Crítico: O modelo de segurança do SAP é transacional e baseado no framework PFCG (Perfis, Roles, Objetos e Níveis Organizacionais). No BigQuery, a segurança é analítica e baseada em Cloud IAM e Row-Level Security (RLS). Sem uma transposição automatizada, haveria vazamento de dados de empresas ou centros restritos.

Principais Metas Arquiteturais

  • ✓

    Sincronização Contínua das Tabelas de Segurança

    Replicar via CDC as 8 tabelas fundamentais de perfis, usuários e autorizações do SAP diretamente para o dataset cortex7_sap_s4_raw.

  • ✓

    De-Para Automático de Identidade

    Vincular o usuário SAP (bname) ao e-mail institucional corporativo (adr6.smtp_addr), correlacionando nativamente com a função SESSION_USER() do BigQuery.

  • ✓

    Tratamento de Níveis Organizacionais Complexos

    Suportar valores pontuais (bukrs = '1000'), faixas (1000 a 1050), coringas (*) e herança de roles compostas.

  • ✓

    Automação Metadata-Driven

    Varredura do INFORMATION_SCHEMA para aplicar políticas de RLS de forma automática em todas as tabelas brutas que contenham colunas organizacionais.

3 Mapeamento Detalhado do Modelo de Autorizações SAP

PFCG & Catálogo SAP

Para reproduzir com total fidelidade as permissões organizacionais, é obrigatório replicar via CDC as seguintes 8 tabelas do catálogo do SAP:

Tabela SAP Nome Técnico & Descrição Campos Críticos Propósito no BigQuery Status
usr02 Dados de Logon do Usuário bname, gltgv, gltgb, uflag Valida vigência e bloqueio (uflag = 0). Obrigatória
usr21 Chave Mestra Usuário-Endereço bname, persnumber, addrnumber Ponte entre o usuário SAP e os dados de contato. Obrigatória
adr6 Central Address Management (E-mails) addrnumber, persnumber, smtp_addr Crítica: E-mail corporativo para SESSION_USER(). Obrigatória
agr_users Atribuição de Roles aos Usuários agr_name, uname, from_dat, to_dat Relaciona o usuário às roles ativas. Obrigatória
agr_agrs Estrutura de Roles Compostas agr_name, child_agr Desmembra roles compostas nas roles simples filhas. Obrigatória
agr_1252 Níveis Organizacionais das Roles agr_name, varbl, low, high Tabela-mestre de escopo: valores de $bukrs, $werks. Obrigatória
agr_1251 Dados de Autorização por Campo agr_name, object, field, low, high Campos não promovidos a níveis org (ex.: f_bkpf_buk). Obrigatória
ust04 Perfis de Usuário Atribuídos Diretamente bname, profile Crítica para SAP_ALL: Captura perfis diretos na SU01 (ex.: SAP_ALL, SAP_NEW). Obrigatória
Convenção de Prefixos ($varbl): No SAP PFCG, variáveis organizacionais usam cifrão (ex.: $bukrs). No BigQuery, o pipeline remove o cifrão com REGEXP_REPLACE(varbl, r'^\$', '') para casar perfeitamente com a coluna da tabela física (bukrs).

Como o BigQuery Trata o Usuário com SAP_ALL (Superusuário)?

No SAP, SAP_ALL não é uma Role PFCG (agr_*), mas sim um Perfil Composto Gerado que concede acesso irrestrito a todos os objetos e campos organizacionais com coringa (*). Um usuário pode receber SAP_ALL diretamente na transação SU01 (aba Perfis) sem possuir nenhuma role PFCG associada.

Estratégia de Resolução em Três Camadas para SAP_ALL:
  1. Ingestão CDC da Tabela ust04: Identifica atribuições diretas de UPPER(profile) IN ('SAP_ALL', 'SAP_NEW') para o usuário corporativo.
  2. Flag Global de Acesso Total: O pipeline de governança insere na tabela sec_user_org_entitlements um registro com org_field = '*' e is_all_access = TRUE. Na política de RLS, a condição (ent.org_field = 'bukrs' OR ent.org_field = '*') retorna TRUE instantaneamente para todas as tabelas.
  3. Curto-Circuito (Short-Circuit Evaluation): Contas técnicas e superusuários com SAP_ALL são avaliados prioritariamente no início do predicado RLS, garantindo que suas consultas rodem sem overhead analítico.

4 Modelagem da Tabela de Entitlements

Armazenamento Otimizado

Para evitar queries com múltiplos joins entre as tabelas agr_* a cada consulta de usuário, materializamos as permissões em uma tabela otimizada e clusterizada por (user_email, org_field):

SQL DDL 
CREATE OR REPLACE TABLE `gcp-data-lake.sap_governance.sec_user_org_entitlements`
(
  user_email STRING NOT NULL OPTIONS(description="E-mail corporativo em minúsculas (coincide com SESSION_USER())"),
  sap_uname STRING NOT NULL OPTIONS(description="ID do usuário no SAP (bname)"),
  org_field STRING NOT NULL OPTIONS(description="Campo organizacional correspondente (bukrs, werks, etc.)"),
  org_value STRING OPTIONS(description="Valor organizacional desnormalizado para correspondência direta no RLS (IN subquery)"),
  val_low STRING OPTIONS(description="Valor pontual ou limite inferior do intervalo"),
  val_high STRING OPTIONS(description="Limite superior do intervalo (NULL se pontual)"),
  is_all_access BOOL NOT NULL OPTIONS(description="Flag de acesso total (*) para este campo"),
  source_roles ARRAY<STRING> OPTIONS(description="Roles de origem para rastreabilidade e auditoria"),
  updated_at TIMESTAMP NOT NULL OPTIONS(description="Data da última sincronização")
)
CLUSTER BY user_email, org_field;

5 Implementação de Row-Level Security (RLS)

Segurança em Nível de Linha

Onde Aplicar: Tabelas RAW vs Views de Consumo?

No BigQuery, as views regulares rodam sob o modelo SECURITY INVOKER. Isso significa que quando o usuário executa uma consulta na View, o BigQuery avalia o RLS da tabela base RAW usando o SESSION_USER() do usuário final.

Vantagem da Aplicação na Camada RAW: Qualquer nova view analítica construída sobre as tabelas brutas herda automaticamente a proteção de RLS sem necessidade de recriar regras. Além disso, analistas com permissão de exploração nas tabelas brutas não conseguirão vazar dados.

DDL da Política de Row-Level Security com Top-Level IN Subqueries Não Correlacionadas

SQL RLS Policy 
CREATE OR REPLACE ROW ACCESS POLICY rap_sap_bukrs
ON `ce-sap-latam-genai.cortex7_sap_s4_raw.bkpf`
GRANT TO (
  'group:gcp-bi-analysts@empresa.com',
  'group:gcp-sap-consumers@empresa.com'
)
FILTER USING (
  -- 1. Bypass para Contas de Serviço e Administradores
  SESSION_USER() LIKE '%@gcp-data-lake.iam.gserviceaccount.com'
  OR SESSION_USER() IN ('admin-governance@empresa.com')

  -- 2. Superusuários com Acesso Total (*) ou SAP_ALL (subquery não correlacionada)
  OR TRUE IN (
    SELECT is_all_access
    FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
    WHERE user_email = SESSION_USER()
      AND (org_field = 'bukrs' OR org_field = '*')
      AND is_all_access = TRUE
  )

  -- 3. Avaliação de Usuários Comuns (subquery não correlacionada com block pruning)
  OR bukrs IN (
    SELECT org_value
    FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
    WHERE user_email = SESSION_USER()
      AND org_field = 'bukrs'
  )
);

6 Automação por Metadados (Metadata-Driven RLS)

Execução Dinâmica

Para não criar scripts manuais para centenas de tabelas, o BigQuery executa uma Stored Procedure que inspeciona o catálogo INFORMATION_SCHEMA.COLUMNS, localiza todas as tabelas contendo a coluna (ex.: bukrs) e aplica a política dinamicamente:

SQL Invocação 
CALL `gcp-data-lake.sap_governance.sp_apply_sap_rls`(
  'ce-sap-latam-genai', 
  'cortex7_sap_s4_raw', 
  'bukrs', 
  "'group:gcp-bi-analysts@empresa.com', 'group:gcp-sap-consumers@empresa.com'"
);

7 Performance e FinOps em Tabelas Grandes

Block Pruning & Slot Optimization

Tabelas como acdoca e bseg possuem centenas de milhões ou bilhões de registros. Sem clustering físico, uma consulta com RLS escanearia todo o volume de dados.

Regra de Ouro FinOps: Toda tabela protegida por RLS por bukrs deve ter bukrs como primeiro ou segundo campo de clustering (ex.: CLUSTER BY bukrs, gjahr, belnr). O BigQuery ignora blocos de dados físicos fora do escopo do usuário, reduzindo os bytes processados em até 90%.

8 Governança, Auditoria e Validação

Conformidade e Rastreabilidade

Para auditar todas as políticas ativas no Data Lake a qualquer momento diretamente no catálogo do BigQuery:

SQL Auditoria 
SELECT 
  target_project,
  target_dataset,
  target_table,
  org_field,
  policy_name,
  action,
  applied_by,
  applied_at
FROM `ce-sap-latam-genai.cortex7_sap_s4_security.sec_rls_audit_log`
WHERE action IN ('APPLIED', 'REVOKED')
QUALIFY ROW_NUMBER() OVER (PARTITION BY target_table, org_field ORDER BY applied_at DESC) = 1
ORDER BY target_table;

  COUNT(DISTINCT u.bname) AS total_sap_users,
  COUNT(DISTINCT IF(a.smtp_addr IS NOT NULL AND a.smtp_addr LIKE '%@empresa.com%', u.bname, NULL)) AS users_with_valid_email,
  ROUND(COUNT(DISTINCT IF(a.smtp_addr IS NOT NULL AND a.smtp_addr LIKE '%@empresa.com%', u.bname, NULL)) / COUNT(DISTINCT u.bname) * 100, 2) AS email_coverage_pct
FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.usr02` u

WHERE u.uflag = 0 
  AND CURRENT_DATE() BETWEEN COALESCE(u.gltgv, DATE '1900-01-01') AND COALESCE(u.gltgb, DATE '9999-12-31');

2 Fase 2: Pipeline de Carga de Entitlements

ETL / Stored Procedure

Passo 2.1: Stored Procedure de Consolidação das Autorizações

SQL Stored Procedure 
CREATE OR REPLACE PROCEDURE `gcp-data-lake.sap_governance.sp_refresh_sap_entitlements`()
BEGIN
  CREATE OR REPLACE TABLE `gcp-data-lake.sap_governance.sec_user_org_entitlements`
  CLUSTER BY user_email, org_field
  AS
  WITH active_users AS (
    SELECT
      LOWER(TRIM(a.smtp_addr)) AS user_email,
      u.bname AS sap_uname
    FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.usr02` u
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.usr21` up
      ON u.bname = up.bname
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.adr6` a
      ON up.persnumber = a.persnumber AND up.addrnumber = a.addrnumber
    WHERE (u.uflag IS NULL OR u.uflag = 0)
      AND CURRENT_DATE() BETWEEN COALESCE(u.gltgv, DATE '1900-01-01') AND COALESCE(u.gltgb, DATE '9999-12-31')
      AND a.smtp_addr IS NOT NULL
      AND a.smtp_addr LIKE '%@empresa.com%'
  ),

  user_roles_expanded AS (
    SELECT
      au.user_email,
      au.sap_uname,
      COALESCE(comp.child_agr, r.agr_name) AS effective_role
    FROM active_users au
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.agr_users` r
      ON au.sap_uname = r.uname
    LEFT JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.agr_agrs` comp
      ON r.agr_name = comp.agr_name
    WHERE CURRENT_DATE() BETWEEN COALESCE(r.from_dat, DATE '1900-01-01') AND COALESCE(r.to_dat, DATE '9999-12-31')
  ),

  raw_org_permissions AS (
    SELECT
      ur.user_email,
      ur.sap_uname,
      ur.effective_role,
      LOWER(REGEXP_REPLACE(a1252.varbl, r'^\$', '')) AS org_field,
      TRIM(a1252.low) AS val_low,
      TRIM(a1252.high) AS val_high
    FROM user_roles_expanded ur
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.agr_1252` a1252
      ON ur.effective_role = a1252.agr_name
    WHERE a1252.varbl IS NOT NULL AND a1252.varbl != ''

    UNION ALL

    SELECT
      ur.user_email,
      ur.sap_uname,
      ur.effective_role,
      LOWER(TRIM(a1251.field)) AS org_field,
      TRIM(a1251.low) AS val_low,
      TRIM(a1251.high) AS val_high
    FROM user_roles_expanded ur
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.agr_1251` a1251
      ON ur.effective_role = a1251.agr_name
    WHERE LOWER(a1251.field) IN ('bukrs', 'werks', 'vkorg', 'ekorg', 'gsber', 'prctr')

    UNION ALL

    -- Fonte 3: Superusuários com Perfil Direto SAP_ALL (ust04)
    SELECT
      au.user_email,
      au.sap_uname,
      'PROFILE:SAP_ALL' AS effective_role,
      '*' AS org_field,
      '*' AS val_low,
      CAST(NULL AS STRING) AS val_high
    FROM active_users au
    INNER JOIN `ce-sap-latam-genai.cortex7_sap_s4_raw.ust04` p
      ON au.sap_uname = p.bname
    WHERE UPPER(p.profile) IN ('SAP_ALL', 'SAP_NEW')
  ),

  master_bukrs AS (
    SELECT DISTINCT bukrs AS org_value FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.t001`
    UNION DISTINCT
    SELECT DISTINCT bukrs FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.bkpf`
  ),

  expanded_values AS (
    -- 1. Valores pontuais simples
    SELECT
      p.user_email,
      p.sap_uname,
      p.org_field,
      p.val_low AS org_value,
      p.val_low,
      p.val_high,
      FALSE AS is_all_access,
      p.effective_role
    FROM raw_org_permissions p
    WHERE p.val_low != '*' 
      AND (p.val_high IS NULL OR p.val_high = '')

    UNION ALL

    -- 2. Faixas de valores (val_low até val_high) expandidas contra empresas existentes
    SELECT
      p.user_email,
      p.sap_uname,
      p.org_field,
      m.org_value,
      p.val_low,
      p.val_high,
      FALSE AS is_all_access,
      p.effective_role
    FROM raw_org_permissions p
    JOIN master_bukrs m
      ON p.org_field = 'bukrs' AND m.org_value BETWEEN p.val_low AND p.val_high
    WHERE p.val_high IS NOT NULL AND p.val_high != ''

    UNION ALL

    -- 3. Acesso Total (*) e Superusuários (SAP_ALL)
    SELECT
      p.user_email,
      p.sap_uname,
      p.org_field,
      CAST(NULL AS STRING) AS org_value,
      p.val_low,
      p.val_high,
      TRUE AS is_all_access,
      p.effective_role
    FROM raw_org_permissions p
    WHERE p.val_low = '*' OR p.org_field = '*'
  )

  SELECT
    user_email,
    sap_uname,
    org_field,
    org_value,
    val_low,
    val_high,
    is_all_access,
    ARRAY_AGG(DISTINCT effective_role) AS source_roles,
    CURRENT_TIMESTAMP() AS updated_at
  FROM expanded_values
  WHERE (org_value IS NOT NULL AND org_value != '') OR is_all_access = TRUE
  GROUP BY user_email, sap_uname, org_field, org_value, val_low, val_high, is_all_access;
END;

SQL Stored Procedure 
CREATE OR REPLACE PROCEDURE `gcp-data-lake.sap_governance.sp_apply_sap_rls`(
  target_project STRING,
  target_dataset STRING,
  org_column_name STRING,
  consumer_grantees STRING
)
BEGIN
  DECLARE exec_id STRING;
  DECLARE formatted_grantees STRING;
  DECLARE dynamic_grantees STRING;
  SET exec_id = GENERATE_UUID();
  SET formatted_grantees = TRIM(COALESCE(consumer_grantees, ''));

  -- Modo Dinâmico: Se vazio, extrai os usuários da sec_user_org_entitlements
  IF formatted_grantees = '' OR formatted_grantees = "''" OR formatted_grantees = '""' THEN
    EXECUTE IMMEDIATE FORMAT("""
      SELECT STRING_AGG(DISTINCT CONCAT("'user:", LOWER(user_email), "'"), ', ')
      FROM `%s.sap_governance.sec_user_org_entitlements`
      WHERE (LOWER(org_field) = LOWER('%s') OR org_field = '*')
        AND user_email IS NOT NULL AND user_email != ''
    """, target_project, org_column_name)
    INTO dynamic_grantees;

    IF dynamic_grantees IS NOT NULL AND dynamic_grantees != '' THEN
      SET formatted_grantees = dynamic_grantees;
    ELSE
      SET formatted_grantees = "'user:admin-governanca@empresa.com'";
    END IF;
  ELSE
    -- Garante que os membros IAM possuam aspas simples se forem passados como string direta
    IF NOT (STARTS_WITH(formatted_grantees, "'") OR STARTS_WITH(formatted_grantees, '"')) THEN
      SET formatted_grantees = FORMAT("'%s'", formatted_grantees);
    END IF;
  END IF;

  FOR target IN (
    SELECT table_name
    FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.INFORMATION_SCHEMA.COLUMNS`
    WHERE LOWER(column_name) = LOWER(org_column_name)
      AND table_schema = target_dataset
      AND table_name NOT LIKE 'agr_%'
      AND table_name NOT LIKE 'usr%'
      AND table_name NOT LIKE 'adr%'
      AND table_name NOT LIKE 'dd%'
      AND table_name NOT LIKE 't001%'
      AND table_name NOT LIKE 'sec_%'
    GROUP BY table_name
  )
  DO
    BEGIN
      EXECUTE IMMEDIATE FORMAT("""
        CREATE OR REPLACE ROW ACCESS POLICY rap_auto_%s_%s
        ON `%s.%s.%s`
        GRANT TO (%s)
        FILTER USING (
          SESSION_USER() LIKE '%%@gcp-data-lake.iam.gserviceaccount.com'
          OR SESSION_USER() IN ('admin-governanca@empresa.com')
          OR TRUE IN (
            SELECT is_all_access
            FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
            WHERE user_email = SESSION_USER()
              AND (org_field = '%s' OR org_field = '*')
              AND is_all_access = TRUE
          )
          OR %s IN (
            SELECT org_value
            FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
            WHERE user_email = SESSION_USER()
              AND org_field = '%s'
          )
        );
      """, 
        LOWER(org_column_name), LOWER(target.table_name),
        target_project, target_dataset, target.table_name,
        formatted_grantees,
        LOWER(org_column_name), LOWER(org_column_name), LOWER(org_column_name)
      );

      INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
      VALUES (
        exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
        'APPLIED', FORMAT('rap_auto_%s_%s', LOWER(org_column_name), LOWER(target.table_name)),
        NULL, SESSION_USER(), CURRENT_TIMESTAMP()
      );
    EXCEPTION WHEN ERROR THEN
      INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
      VALUES (
        exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
        'FAILED', FORMAT('rap_auto_%s_%s', LOWER(org_column_name), LOWER(target.table_name)),
        @@error.message, SESSION_USER(), CURRENT_TIMESTAMP()
      );
    END;
  END FOR;
END;

Passo 3.2: Criar a Stored Procedure de Remoção Emergencial (sp_revoke_sap_rls)

Essencial para situações em que for necessário reverter as políticas de RLS rapidamente. Como o BigQuery não expõe INFORMATION_SCHEMA.ROW_ACCESS_POLICIES em SQL e exige DROP ALL ROW ACCESS POLICIES ao remover a última política de uma tabela, a procedure realiza uma remoção inteligente com fallback seguro e idempotente:

SQL Procedure Rollback 
CREATE OR REPLACE PROCEDURE `gcp-data-lake.sap_governance.sp_revoke_sap_rls`(
  target_project STRING,
  target_dataset STRING,
  org_column_name STRING
)
BEGIN
  DECLARE exec_id STRING;
  SET exec_id = GENERATE_UUID();

  -- Identifica as tabelas candidatas a partir de INFORMATION_SCHEMA.COLUMNS e do histórico em sec_rls_audit_log
  FOR target IN (
    SELECT DISTINCT table_name
    FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.INFORMATION_SCHEMA.COLUMNS`
    WHERE LOWER(column_name) = LOWER(org_column_name)
      AND table_schema = target_dataset
      AND table_name NOT LIKE 'agr_%'
      AND table_name NOT LIKE 'usr%'
      AND table_name NOT LIKE 'adr%'
      AND table_name NOT LIKE 'dd%'
      AND table_name NOT LIKE 't001%'
      AND table_name NOT LIKE 'sec_%'
    UNION DISTINCT
    SELECT DISTINCT target_table AS table_name
    FROM `gcp-data-lake.sap_governance.sec_rls_audit_log`
    WHERE target_project = target_project
      AND target_dataset = target_dataset
      AND LOWER(org_field) = LOWER(org_column_name)
      AND action = 'APPLIED'
  )
  DO
    BEGIN
      DECLARE policy_name STRING;
      SET policy_name = FORMAT('rap_auto_%s_%s', LOWER(org_column_name), LOWER(target.table_name));

      BEGIN
        EXECUTE IMMEDIATE FORMAT("""
          DROP ROW ACCESS POLICY IF EXISTS %s ON `%s.%s.%s`;
        """, policy_name, target_project, target_dataset, target.table_name);

        INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
        VALUES (
          exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
          'REVOKED', policy_name, NULL, SESSION_USER(), CURRENT_TIMESTAMP()
        );
      EXCEPTION WHEN ERROR THEN
        IF CONTAINS_SUBSTR(LOWER(@@error.message), 'drop all') 
           OR CONTAINS_SUBSTR(LOWER(@@error.message), 'last row access policy') THEN
          BEGIN
            EXECUTE IMMEDIATE FORMAT("""
              DROP ALL ROW ACCESS POLICIES ON `%s.%s.%s`;
            """, target_project, target_dataset, target.table_name);

            INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
            VALUES (
              exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
              'REVOKED', FORMAT('%s (DROP ALL)', policy_name), NULL, SESSION_USER(), CURRENT_TIMESTAMP()
            );
          EXCEPTION WHEN ERROR THEN
            INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
            VALUES (
              exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
              'FAILED_REVOKE', policy_name, @@error.message, SESSION_USER(), CURRENT_TIMESTAMP()
            );
          END;
        ELSE
          INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
          VALUES (
            exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
            'FAILED_REVOKE', policy_name, @@error.message, SESSION_USER(), CURRENT_TIMESTAMP()
          );
        END IF;
      END;
    END;
  END FOR;
END;

1 Visão Geral e Fundamentos Arquiteturais

Deep-Dive Técnico

Esta seção descreve a fundo a mecânica de transposição de regras de segurança entre o ambiente transacional SAP (ECC / S/4HANA) e o data warehouse analítico Google Cloud BigQuery no âmbito do projeto corporativo de Data Lakehouse com Google Cloud e SAP.

Princípio Central: Segurança Dinâmica e Desacoplada: Em vez de criar permissões manuais de usuário por usuário ou duplicar tabelas analíticas para cada empresa, a solução implementa Row-Level Security (RLS) nativa no BigQuery baseada em uma tabela de direitos (entitlements) sincronizada de forma contínua com o SAP.

O Paradigma SAP (PFCG) vs O Paradigma BigQuery (RLS)

No SAP, as autorizações são avaliadas pelo kernel da aplicação através de comandos AUTHORITY-CHECK baseados em Objetos de Autorização (ex: F_BKPF_BUK para lançamentos contábeis) e campos organizacionais (como BUKRS para Empresa e WERKS para Centro). Os usuários recebem Roles Simples ou Compostas na transação PFCG.

No BigQuery, não existe um kernel de aplicação intermediário: as ferramentas de BI (Power BI, Looker, SAP Analytics Cloud) e consultas de analistas conectam-se diretamente via SQL. A segurança de linha precisa ser avaliada pelo motor colunar Dremel em tempo de execução via ROW ACCESS POLICY, utilizando a função SESSION_USER() que retorna o e-mail corporativo autenticado (Google Workspace).

Isso elimina o erro de correlação do BigQuery e habilita poda de partições em tabelas particionadas!

3 As Três Stored Procedures em Detalhes

Engenharia de Automação

A esteira de automação é dividida em três procedimentos armazenados com atribuições bem definidas e isoladas:

3.1 sp_refresh_sap_entitlements(p_target_dataset): O Motor de Entitlements

Papel: É a rotina que extrai as informações brutas do SAP, desdobra a lógica de segurança e materializa os resultados na tabela sec_user_org_entitlements.

Como funciona internamente (Etapas das CTEs):

  • 1

    Filtro de Contas Válidas (active_users)

    Inspeciona a tabela usr02 e seleciona exclusivamente usuários com flag de bloqueio uflag = 0 e cuja data de expiração (gltgb) seja maior ou igual a hoje. Usuários demitidos ou inativos são expurgados aqui.

  • 2

    Vínculo de E-mail Corporativo (user_emails)

    Cruza usr02 com usr21 e adr6. Converte os endereços para minúsculas (LOWER(TRIM(smtp_addr))) e utiliza QUALIFY ROW_NUMBER() OVER(PARTITION BY bname ORDER BY IF(flgdefault='X', 0, 1)) = 1 para garantir um e-mail único e prioritário por usuário.

  • 3

    Resolução de Roles Compostas (role_hierarchy & user_roles)

    Desdobra hierarquias da agr_define. Se o usuário tiver uma role composta, a procedure extrai todas as roles simples componentes e valida se o período de concessão na agr_users está ativo.

  • 4

    Coleta da Tabela Mestre de Empresas (master_bukrs)

    Executa uma leitura única em t001 retornando todas as empresas cadastradas no ambiente SAP corporativo.

  • 5

    Expansão Determinística de Faixas e Coringas (expanded_bukrs)

    Resolve valores concretos através de três lógicas:

    • Valores Pontuais: Converte val_low diretamente para org_value.
    • Faixas Organizacionais: Faz JOIN master_bukrs ON bukrs BETWEEN val_low AND val_high. Para cada empresa real existente no intervalo, gera uma linha com org_value.
    • Superusuários e Coringas (* e SAP_ALL): Marca is_all_access = TRUE e associa todas as empresas da t001.
  • 6

    Gravação Atômica

    Agrupa os direitos por usuário e campo organizacional, consolidando as roles de origem em um array (ARRAY_AGG(DISTINCT agr_name)) e carimbando a execução com CURRENT_TIMESTAMP().

3.2 sp_apply_sap_rls(...): O Motor de Aplicação de Segurança

Papel: Lê a configuração da tabela sec_table_rls_config e executa comandos DDL dinâmicos de CREATE OR REPLACE ROW ACCESS POLICY nas tabelas de dados.

Atenção à Limitação de Subquery Correlacionada do BigQuery: O BigQuery rejeita políticas de segurança que correlacionam diretamente a coluna da tabela protegida dentro de um WHERE EXISTS (...) (ex: WHERE tvko.bukrs = ent.val_low).
Por isso, a sp_apply_sap_rls gera predicados baseados no operador Top-Level IN não correlacionado, que é totalmente suportado e possui desempenho superior!

Estrutura da Cláusula de RLS Gerada Dinamicamente:

SQL Gerado Automaticamente pela Procedure 
CREATE OR REPLACE ROW ACCESS POLICY `rap_sap_tvko_bukrs`
ON `ce-sap-latam-genai.cortex7_sap_s4_raw.tvko`
GRANT TO ('group:genai4sap_finance@felipechagas.altostrat.com')
FILTER USING (
  -- Ramo 1: Superusuários (SAP_ALL ou Coringa '*')
  TRUE IN (
    SELECT is_all_access 
    FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
    WHERE user_email = SESSION_USER() 
      AND org_field = 'bukrs' 
      AND is_all_access = TRUE
  )
  OR
  -- Ramo 2: Empresas específicas autorizadas ao usuário
  bukrs IN (
    SELECT org_value 
    FROM `gcp-data-lake.sap_governance.sec_user_org_entitlements`
    WHERE user_email = SESSION_USER() 
      AND org_field = 'bukrs'
  )
);

Sanitização de Grantees IAM: No BigQuery, o parâmetro GRANT TO não aceita a palavra group: desacompanhada de aspas (pois o parser confunde com a palavra-chave GROUP BY). A procedure verifica automaticamente se o valor informado possui aspas simples e as adiciona se necessário, prevenindo falhas de compilação.

3.3 sp_revoke_sap_rls(...): O Mecanismo de Rollback Seguro

Papel: Procedimento de emergência que remove as políticas de RLS de uma determinada tabela ou de todo o dataset caso seja necessário realizar uma manutenção em lote ou reverter uma implantação.

Por que não usar INFORMATION_SCHEMA.ROW_ACCESS_POLICIES? No Google Cloud BigQuery, não existe uma visão de catálogo SQL chamada ROW_ACCESS_POLICIES (políticas de acesso a linhas só são listadas via API REST ou rastreadas na auditoria). Por isso, a procedure identifica com segurança as tabelas candidatas cruzando INFORMATION_SCHEMA.COLUMNS com o histórico da tabela de controle sec_rls_audit_log e executa DROP ROW ACCESS POLICY IF EXISTS de forma totalmente idempotente:

SQL Procedure Rollback 
CREATE OR REPLACE PROCEDURE `gcp-data-lake.sap_governance.sp_revoke_sap_rls`(
  target_project STRING,
  target_dataset STRING,
  org_column_name STRING
)
BEGIN
  DECLARE exec_id STRING;
  SET exec_id = GENERATE_UUID();

  -- Identifica as tabelas candidatas a partir de INFORMATION_SCHEMA.COLUMNS e de sec_rls_audit_log
  FOR target IN (
    SELECT DISTINCT table_name
    FROM `ce-sap-latam-genai.cortex7_sap_s4_raw.INFORMATION_SCHEMA.COLUMNS`
    WHERE LOWER(column_name) = LOWER(org_column_name)
      AND table_schema = target_dataset
      AND table_name NOT LIKE 'agr_%'
      AND table_name NOT LIKE 'usr%'
      AND table_name NOT LIKE 'adr%'
      AND table_name NOT LIKE 'dd%'
      AND table_name NOT LIKE 't001%'
      AND table_name NOT LIKE 'sec_%'
    UNION DISTINCT
    SELECT DISTINCT target_table AS table_name
    FROM `gcp-data-lake.sap_governance.sec_rls_audit_log`
    WHERE target_project = target_project
      AND target_dataset = target_dataset
      AND LOWER(org_field) = LOWER(org_column_name)
      AND action = 'APPLIED'
  )
  DO
    BEGIN
      DECLARE policy_name STRING;
      SET policy_name = FORMAT('rap_auto_%s_%s', LOWER(org_column_name), LOWER(target.table_name));

      BEGIN
        EXECUTE IMMEDIATE FORMAT("""
          DROP ROW ACCESS POLICY IF EXISTS %s ON `%s.%s.%s`;
        """, policy_name, target_project, target_dataset, target.table_name);

        INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
        VALUES (
          exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
          'REVOKED', policy_name, NULL, SESSION_USER(), CURRENT_TIMESTAMP()
        );
      EXCEPTION WHEN ERROR THEN
        IF CONTAINS_SUBSTR(LOWER(@@error.message), 'drop all') 
           OR CONTAINS_SUBSTR(LOWER(@@error.message), 'last row access policy') THEN
          BEGIN
            EXECUTE IMMEDIATE FORMAT("""
              DROP ALL ROW ACCESS POLICIES ON `%s.%s.%s`;
            """, target_project, target_dataset, target.table_name);

            INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
            VALUES (
              exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
              'REVOKED', FORMAT('%s (DROP ALL)', policy_name), NULL, SESSION_USER(), CURRENT_TIMESTAMP()
            );
          EXCEPTION WHEN ERROR THEN
            INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
            VALUES (
              exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
              'FAILED_REVOKE', policy_name, @@error.message, SESSION_USER(), CURRENT_TIMESTAMP()
            );
          END;
        ELSE
          INSERT INTO `gcp-data-lake.sap_governance.sec_rls_audit_log`
          VALUES (
            exec_id, target_project, target_dataset, target.table_name, LOWER(org_column_name),
            'FAILED_REVOKE', policy_name, @@error.message, SESSION_USER(), CURRENT_TIMESTAMP()
          );
        END IF;
      END;
    END;
  END FOR;
END;

4 Operação Contínua (Day-2 Operations)

Guia de Sustentação

Uma dúvida fundamental da equipe de sustentação e engenharia de dados é: "O que eu preciso executar no dia a dia quando ocorrerem mudanças nas permissões do SAP?"

Resposta Direta e Conclusiva: Para refletir qualquer alteração de roles, criação de usuários ou concessão de empresas feita no SAP, VOCÊ PRECISA APENAS AGENDAR OU EXECUTAR A PROCEDURE sp_refresh_sap_entitlements().

Você NÃO precisa:
  • ❌ NÃO precisa executar a sp_apply_sap_rls() novamente.
  • ❌ NÃO precisa recriar as políticas de segurança nas tabelas de dados.
  • ❌ NÃO precisa reiniciar conectores ou alterar views analíticas.

Comparativo dos Cenários de Operação

Evento no Negócio O que acontece sob o capô Ação Requerida da Equipe de Dados
Colaborador recebe nova empresa no SAP O conector CDC replica as alterações das tabelas agr_users e agr_1251 para o dataset cortex7_sap_s4_raw em segundos. Nenhuma ação manual! A Scheduled Query roda a sp_refresh_sap_entitlements() periodicamente (ex: a cada 1 hora). Assim que ela termina, o usuário já vê os novos dados no BigQuery.
Colaborador é desligado da organização A equipe do SAP bloqueia o usuário na transação SU01 (seta uflag != 0 na usr02). O CDC replica a linha. No próximo refresh da sp_refresh_sap_entitlements(), o e-mail do usuário é removido de sec_user_org_entitlements. Pelo princípio de Deny by Default, o acesso é revogado imediatamente.
Uma NOVA tabela de negócio é adicionada ao BigQuery (ex: vbak ou ekko) A tabela foi replicada via CDC, mas ainda não possui nenhuma política de RLS vinculada. Ação em 2 passos:
1. Inserir um registro com os metadados da tabela na sec_table_rls_config.
2. Executar a sp_apply_sap_rls(...) para a nova tabela uma única vez.

5 Tratamento de Casos Críticos de Negócio SAP

Regras de Exceção
Cenário Crítico SAP Como o SAP gerencia Implementação na Solução BigQuery
Superusuário (SAP_ALL) O usuário possui perfil mestre irrestrito, ignorando verificações de objetos. A procedure detecta agr_name = 'sap_all' e define is_all_access = TRUE. Na política de RLS, o predicado TRUE IN (SELECT is_all_access ...) é satisfeito de imediato, permitindo leitura completa sem restrição de empresa.
Coringa Geral (low = '*') A role concede acesso a qualquer empresa presente ou futura do ambiente. A procedure mapeia o coringa, expande para todas as empresas da tabela t001 e sinaliza is_all_access = TRUE.
Faixas Numéricas (ex: 1000 a 1050) O SAP grava os limites inferior e superior na tabela agr_1251. A procedure faz um JOIN master_bukrs ON bukrs BETWEEN low AND high. Cada empresa real do intervalo vira uma linha na coluna org_value, evitando filtros lentos de range na consulta analítica.
Usuário sem E-mail na ADR6 Usuários técnicos de sistema (ex: ALEREMOTE, SAP*) ou cadastros incompletos. A CTE user_emails exige e-mail corporativo válido. Usuários sem e-mail não são carregados na tabela de segurança, impedindo personificação em ferramentas de BI.
Princípio do Deny by Default Se o usuário não tiver autorização no SAP, a transação retorna código de erro 4 ou 12. Se o e-mail de SESSION_USER() não existir na sec_user_org_entitlements, as subqueries retornam conjunto vazio e o BigQuery entrega 0 linhas ao usuário, com total sigilo.

6 Governança, FinOps e Otimização de Performance

Arquitetura de Alta Eficiência

A arquitetura foi meticulosamente projetada para minimizar custos de processamento (FinOps) e garantir que consultas analíticas continuem velozes mesmo sobre tabelas com centenas de milhões de linhas (como bseg e bkpf).

Três Pilares de Otimização no BigQuery

  • ⚡

    1. Clustering Estratégico por user_email e org_field

    A tabela sec_user_org_entitlements é clusterizada nas duas colunas utilizadas no predicado WHERE da política. Quando o BigQuery executa a subquery para o usuário da sessão, ele realiza um salto direto nos blocos de metadados, processando menos de 10 KB de dados em frações de milissegundo.

  • ⚡

    2. Avaliação Desacoplada (Non-Correlated Subquery)

    Diferente de uma subquery correlacionada (que forçaria o motor a inspecionar linha a linha da tabela transacional externa), a subquery desacoplada é executada apenas uma vez no início do plano de consulta. O otimizador Dremel resolve a lista de empresas autorizadas como uma constante literal (ex: ['1000', '1010']) antes de ler os dados de fato.

  • ⚡

    3. Preservação de Partition & Cluster Pruning

    Como o filtro final se comporta como WHERE bukrs IN ('1000', '1010'), se a tabela de negócio for particionada ou clusterizada por bukrs, o BigQuery descarta imediatamente todos os blocos de dados das empresas às quais o usuário não tem acesso. Isso reduz a quantidade de dados escaneados em até 98%, diminuindo diretamente o custo financeiro da consulta.

7.3 Inventário Global de Políticas de RLS em Vigor

SQL Catálogo de RLS 
SELECT 
  target_project AS project_id,
  target_dataset AS dataset_name,
  target_table AS table_name,
  org_field,
  policy_name AS row_access_policy_name,
  action,
  applied_by,
